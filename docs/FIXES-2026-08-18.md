# FIXES — 2026-08-18 adversarial review of `@bao/court` v0.4.0

Memo for the post-v0.4.0 hardening applied to the public
`baocommunity/bao-court` repository. Every finding was reproduced against the
real code before fixing; every fix has regression tests; the full suite is
green (600/600).

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 1 | HIGH | Ambiguous delimiter-joined hashing in `buildAttestationMessage`, `createBondOwnershipChallenge`, `deriveLnPreimage`: a field containing `|` aliased the adjacent field, so two DISTINCT tuples hashed to the same digest (FROST-signed message / bond-ownership challenge / hold-invoice preimage) | **FIXED** |

Retracted during review: nothing. Also re-verified sound: Pedersen DKG
(POK enforced, refresh math), FROST signing machine (canonical session
binding, nonce-equivocation aborts, nonce-use guard), escrow integer math
and conservation invariant, attestation validator (tag singleton checks,
`nonce == sig[0:64]`, field binding), complaint possession binding, and the
DKG proof-of-knowledge `|`-join (fixed-format hex fields under a fixed
domain — the hex alphabet cannot contain the delimiter).

## Fix

### 1. Canonical length-prefixed hashing (`CanonicalWriter`)

Three hashing sites joined attacker-controlled UTF-8 fields with `|`,
violating the Court's own canonical-encoding invariant (`CanonicalWriter`:
"Delimiter-joined attacker-controlled strings must never be hashed
directly"). Concrete pre-fix collision:

```
buildAttestationMessage('m|YES', '1', 1)  →  'm|YES|1|1'
buildAttestationMessage('m', 'YES|1', 1)  →  'm|YES|1|1'   // identical digest
```

Two distinct verdicts hashed to the same FROST-signed message; the same
ambiguity class affected the bond challenge (disputeId/jurorPubkey) and the
LN preimage (disputeId/role).

- `crypto.ts::buildAttestationMessage` — now SHA-256 over
  `CanonicalWriter` fields under a new domain tag
  `BAO-Court/AttestationMessage/v1` (the attestation was the only one of the
  three domains lacking domain separation).
- `escrow.ts::createBondOwnershipChallenge` — same treatment under the
  existing `BAO-Court/BondOwnership/v1` domain.
- `lnSettlement.ts::deriveLnPreimage` — same treatment under the existing
  `BAO-Court/LnPreimage/v1` domain.

`CanonicalWriter` (courtSession.ts) emits UTF-8 length-prefixed fields, so
every tuple of values is unambiguous regardless of field content. The paper
(§3.3) and `docs/ESCROW-SLASHING.md` were updated to describe the canonical
encoding; the old "joined with `|`" description was removed.

**Wire impact:** the three functions keep their signatures but change their
output digests (new signed-message format, new bond challenges, new invoice
preimages). This is a consumer-visible behavior change → **v0.5.0** on
release, plus the vendor-sync into bao.markets. No attestations or invoices
exist in production yet, so this is the right time to break the format.

## Verification (round 1)

- Regression tests: `__tests__/regressions.test.ts` — three tests pin
  pre-fix collision pairs (each pair hashed identically under the old
  encoding; each must now differ).
- `npm test`: **585/585** (36 files, ~46 s).
- `npm run typecheck`, `npm run typecheck:scripts`: clean.
- `npm run simulate:court`: **ALL GREEN** — same deterministic pipeline
  output as before the fix (group key, Liquid address, settle/cancel
  decisions), and the attestation validates end-to-end (signer and
  validator recompute the same canonical message).

# Round 2 — deep code-logic review (same day)

A second review focused on the code paths themselves (selection, DKG,
signing, vote, escrow, appeal timing, Liquid escrow, bond verification,
session encoding) rather than test coverage.

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 2 | HIGH | Taproot construction is not BIP-341 compliant: untagged SHA-256 for the TapTweak/TapLeaf/TapBranch hashes, no tweak for key-only outputs, and an even-Y retweak BIP-341 does not perform — the derived addresses/roots diverge from every standard wallet and script-path spends would fail consensus validation | **FIXED** |
| 3 | MEDIUM-HIGH | `courtVoteMachine` `tick` expired `reveal_closed`: after `close_reveals` (legal at/after the deadline) a clock tick permanently bricked the ceremony before `finalize_tally` — the DKG machine already exempts its post-deadline `certified` phase | **FIXED** |
| 4 | LOW | `locktimeToPush` documented but did not implement the 5-byte push for time-based locktimes (>= 0x80000000) — a 4-byte push is a negative script number and CLTV would always fail | **FIXED** |
| 5 | LOW | Paper §5 documented the vote reveal as kind 39004 (the commit kind); reveals are kind 39014 | **FIXED** (doc) |

## Fixes

### 2. BIP-341 compliance (`liquidEscrow.ts`)

The construction now follows the spec exactly, pinned against the official
bitcoin-core `bip341_wallet_vectors.json`:

- `taggedHash(tag, ...parts)` = `SHA256(SHA256(tag) || SHA256(tag) || parts)`.
- `tapMerkleRoot`: leaves are `hash_TapLeaf(0xc0 || compact_size(len) ||
  script)`, inner nodes `hash_TapBranch(l || r)` over lexicographically
  sorted children (the old untagged double-SHA256 tree commits to a different
  root than consensus recomputes from the control block).
- `taprootProgram`: output key is ALWAYS `Q = P + int(hash_TapTweak(P || h))G`
  (empty `h` when there is no script tree). Removed the even-Y retweak —
  BIP-341 does not force even Y on Q (parity lives in the control block;
  key-path signing negates the internal secret iff P is odd). The old code
  produced `x(P - tG)` whenever Q had odd Y, diverging from every wallet.
- `locktimeToPush`: time-based locktimes (>= 0x80000000) now emit the
  positive 5-byte push the comment always promised.

### 3. Vote-machine tick (`courtVoteMachine.ts`)

`tick` now exempts `reveal_closed` (deadline already satisfied, finalization
still legal), mirroring the DKG machine's `certified` exemption.

## Verification (round 2)

- New regression tests: two official BIP-341 wallet vectors (key-only and
  single-leaf), locktime 5-byte/4-byte encodings, and the vote tick
  never-expires-before-finalization case.
- `npm test`: **590/590** (36 files).
- `npm run typecheck`, `npm run typecheck:scripts`: clean.
- `npm run simulate:court`: **ALL GREEN** — deterministic, unchanged output
  (the sim uses the P2WSH rail, which is unaffected).

Also re-verified sound (no change): selection quadratic lottery (log(0)
clamped, deterministic tie-break), FROST signing (nonce guard, partial-sig
verification, duplicate-idx rejection), DKG core + refresh math, escrow
redistribution conservation (dust = pool mod coherent count), bond
verification, session canonical encoding, complaint possession binding, and
the DKG POK `|`-join (hex-only fields).

# Round 3 — end-to-end flow review (same day)

A flow-level review of the orchestrator (`appealCoordinator.ts`) and the
imperative vote path (`dispute.ts`), tracing handoffs between selection,
dkg, vote, signing, attestation, and settlement.

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 6 | MEDIUM-HIGH | The coordinator signed `disputeCase.proposedOutcome` (the CHALLENGER'S claim) instead of the tally winner; `verdict` from `tallyVotes` was computed and discarded. Masked in the demo because the simulated jury votes uniformly for the proposed outcome, but wrong for any real heterogeneous vote | **FIXED** |
| 7 | MEDIUM | `dispute.ts::hashCommit` hashed `${outcome}|${salt}` — the same delimiter-ambiguity class as finding 1, in the imperative vote path (coordinator, simulator, `tallyVotes`) where all salts/hashes are recomputed. Missed in round 1 because `tallyVotes` verifies against its own `hashCommit`, so the ambiguity was self-consistent | **FIXED** |
| 8 | DESIGN GAP | The dispute attestation does not bind the vote tally: the signed message is H(market, outcome, round, dispute) and the kind-39007 event carries no verdict/supporting-evidence fields. `settleAppeal`'s `message_does_not_bind_verdict` check recomputes the message but cannot detect an attestation for an outcome that lost the vote. The court's FROST signature certifies the outcome without certifying that it WON the vote | **proposal below** |

## Fixes

### 6. Coordinator signs the verdict (`appealCoordinator.ts`)

`FrostAppealState` gains `verdictOutcome` (set when `tallyVotes` runs); the
signing round attests `verdictOutcome` and never the proposed outcome.
Regression test injects an appeal in the `signing` phase whose verdict
(`NO`) differs from the proposed outcome (`YES`) and asserts the attestation
carries `NO`.

### 7. Canonical vote commit (`dispute.ts`)

`hashCommit` now uses `CanonicalWriter` (length-prefixed `outcome` + `salt`)
under the same `BAO-Court/VoteCommit/v1` domain as the machine path.
Regression test pins the pre-fix collision pair (`'YES|s' + 'alt'` vs
`'YES' + 's|alt'`).

## Round 4 — verdict certification implemented (finding 8, same day)

The panel recommendation is now shipped end to end: the kind-39007
attestation certifies the **tally**, not just an outcome.

### 8. Verdict commitment in the signed message (`crypto.ts`, `courtVoteMachine.ts`)

- `hashDisputeVerdict` — canonical, order-independent commitment
  `H(BAO-Court/DisputeVerdict/v1, disputeId, outcome, count, sorted
  supporting reveal event ids)` over `CanonicalWriter`.
- `buildAttestationMessage` gains an optional `verdictHash` field (bound
  only for kind-39007); `SigningRoundParams` / `DisputeSigningParams`
  thread it through `aggregateAttestation` / `runNormalSigningRound` /
  `runDisputeOverrideSigning` / the `independentSigning` wrapper.

### 9. Frozen at tally time (`appealCoordinator.ts`)

The coordinator now sets `verdictOutcome` **and** `verdictHash` (from
`hashDisputeVerdict` over the supporting reveals) when the tally runs,
passes both into the signing round, and `settleAppeal` rejects any dispute
attestation without a valid verdict hash or whose message does not recompute
with the carried commitment.

### 10. Event surface + enforcement (`events.ts`, `validator.ts`)

- `buildDisputeAttestationEvent` carries the `verdict` tag, `verdictHash`
  in content, and the supporting reveal ids as `e`-mention tags (signed by
  the Nostr event id — tampering invalidates the event).
- `validateAttestationEvent` **requires** a 64-hex `verdict` tag on
  kind-39007, checks tag↔content agreement, and recomputes the signed
  message with the carried commitment. Kind-89 stays untouched (no vote,
  no verdict).
- `parseAttestationEvent` surfaces `verdictHash` + `supportingEventIds` for
  observers.

### 11. Simulator + public API (`scripts/simulateCourt.ts`, `index.ts`)

- The simulator signs with the verdict commitment and validates it
  end to end; `hashDisputeVerdict` and `deriveSimulatedRevealEventId` are
  exported for consumers (bao.markets computes the commitment at tally
  time exactly like the coordinator).

Wire impact: new signed-message format for dispute attestations — must land
in the same 0.5.0 release as the round-1 canonical-hashing change, before
any attestations exist in production.

# Round 5 — clock units, ledger integrity, and the taproot tree shape

A third pass over the modules touched by the earlier fixes, chasing
consistency bugs (units, snapshot integrity, fail-closed guards) and
re-auditing the round-2 taproot change against the authoritative BIP-341
reference.

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 12 | MEDIUM | `LnHoldLedger.hold/decide/expire`, `EscrowLedger.lock/return/slash/forfeit/redistribute`, and the fake `LnRail.getStatus` used `Date.now()` (milliseconds) against `expiresAt`/`resolvedAt` stored in unix SECONDS — a default-clock hold always looked already expired and the default-clock decide always threw | **FIXED** |
| 13 | HIGH | `tapMerkleRoot` produced a non-BIP-341 root for 3+ leaves. Round 2 left the naive pair-up-with-self algorithm (duplicates the odd leaf); the round-5 rewrite to a largest-power-of-two split was ALSO wrong. Bitcoin Core's `taproot_tree_helper` (the generator of `bip341_wallet_vectors.json`) splits at `len // 2`: 3 leaves = `TapBranch(h0, TapBranch(h1, h2))` — pinned by the official vector, whose leaf-0 control block carries a single sibling | **FIXED** (split-at-mid, official vector) |
| 14 | LOW-MEDIUM | `filterEligibleJurors` accepted a future-dated `registeredAt` — `now - registeredAt` goes negative, which passes the minimum-age threshold and makes the candidate look arbitrarily old | **FIXED** |
| 15 | LOW | `calculateBondAmount` / `calculateJurorStake` silently clamped negative and non-integer rounds via `Math.max(0, round - 1)` and could overflow past safe-integer range | **FIXED** (fail-closed) |
| 16 | LOW | `CanonicalWriter.u8` accepted out-of-range values; `Uint8Array.of` truncates them mod 256, corrupting the canonical encoding | **FIXED** |
| 17 | LOW | `EscrowLedger` and `LnHoldLedger` constructors accepted duplicate ids in a snapshot (last-wins, silently dropping a deposit/hold) | **FIXED** |
| 18 | LOW | `buildLnAuditEvent` used a constant `d` tag, so later audit events overwrote earlier ones on replaceable kinds | **FIXED** (d-tag keyed by hold id) |
| 19 | LOW-MEDIUM | The round-3 coordinator fix kept a `verdictOutcome ?? proposedOutcome` fallback, so a missing/empty verdict (every reveal invalid) would still attest the challenger's claim | **FIXED** (abort signing) |

## Fixes

### 12. Wall-clock unit alignment (`lnSettlement.ts`, `lnRail.ts`, `escrow.ts`)

Ledger timestamps are unix seconds; the methods now default to
`Math.floor(Date.now() / 1000)` instead of `Date.now()`, and the fake
`LnRail.getStatus` compares `expiry` in the same seconds unit. The injected
`now` parameters are unchanged, so hosts passing explicit seconds are
unaffected.

### 13. Taproot merkle tree shape (`liquidEscrow.ts`)

`tapMerkleRoot` now mirrors Bitcoin Core's `taproot_tree_helper` exactly:
split the leaf list at `len // 2` and recurse (empty list rejected). The
naive pair-up-with-self and the largest-power-of-two split both diverge from
the official 3-leaf vector (`merkleRoot ccbd66c6…`, `internalPubkey
e0dfe2…`), whose script tree is `[id0, [id1, id2]]`. Regression test now
pins that vector directly rather than a hand-computed value.

### 14–19. Fail-closed guards

Future `registeredAt` excluded; non-integer/negative rounds and overflowing
bond/stake amounts rejected; `CanonicalWriter.u8` range-checked; duplicate
snapshot ids rejected; audit-event d-tags keyed by hold id; coordinator
aborts signing (`no_verdict`) instead of attesting a claim when the tally
has no winner.

## Verification (round 5)

- New regression tests: 3 (default-wall-clock LN ledger, future-`registeredAt`
  jury exclusion, official BIP-341 3-leaf merkle vector).
- `npm test`: **597/597** (36 files).
- `npm run typecheck`, `npm run typecheck:scripts`: clean.
- `npm run simulate:court`: **ALL GREEN** — deterministic (the P2WSH rail
  and the 2-leaf judge/refund taproot path are unaffected).

# Round 6 — canonical-writer integer bounds + host-boundary sweep

A wider sweep over the modules not yet line-read: the FROST signing core
(`crypto.ts`, `signing.ts`), the NIP-44/NIP-59 boundary (`nip44Crypto.ts`,
`nip59.ts`, `courtSigner.ts`), recovery envelopes (`courtRecovery.ts`), the
strict event boundary (`courtProtocolEvents.ts`), selection, and escrow.

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 20 | MEDIUM | `CanonicalWriter.u32` / `u64` silently wrapped out-of-range values — `DataView.setUint32(-1)` → `0xFFFFFFFF`, `setUint32(2^32)` → `0`, and fractional values truncate; `setBigUint64` wraps negatives/oversized the same way. Round 5 range-checked `u8` but left the wider writers with the identical silent-corruption class: a wrapped length/count makes two distinct tuples share one canonical encoding, defeating the length-prefixed invariant the whole writer exists to enforce | **FIXED** |

## Fixes

### 20. Integer bounds in `CanonicalWriter` (`courtSession.ts`)

`u32` now rejects anything outside `[0, 0xFFFFFFFF]` and non-integers;
`u64` rejects anything outside the safe-integer range (a safe non-negative
integer is always `< 2^64`, so `setBigUint64` can no longer wrap). Both
throw `CourtSessionValidationError('invalid_number')` exactly like `u8`.
Two regression tests pin the pre-fix wraparound values and the intact
big-endian boundary encodings.

## Verified sound (no change)

- `nip59.ts` / `courtSigner.ts` strict unwrap: recipient p-tag, seal
  Schnorr signature on a reconstructed (cache-free) copy, seal-author ===
  rumor-author binding, and recomputed rumor-id commitment.
- `courtRecovery.ts` certify-before-backup and full recomputation battery
  (group key = Σ commits[0], verification shares re-derived per idx, full
  point — not x-only — local-share parity check).
- `courtProtocolEvents.ts` strict boundary: signature re-verification,
  canonical-uint parsing, unique-tag enforcement, exact payload keys,
  tag↔content↔session agreement.
- `selection.ts` deterministic lottery and `escrow.ts` conservation (dust =
  pool mod coherent count) re-confirmed.

## Verification (round 6)

- New regression tests: 2 (u8/u32/u64 out-of-range rejection, big-endian
  boundary encodings).

- `npm run typecheck`, `npm run typecheck:scripts`: clean.

# Round 7 — independent-juror signing path and keeper/host-key sweep

A pass over the two FROST signing wrappers (`independentSigning.ts`,
`dispute.ts`), the keeper designation/reveal module (`courtKeeper.ts`), and
the host-key lifecycle (`courtHostKey.ts`).

## Found

| # | Severity | Finding | Status |
|---|----------|---------|--------|
| 21 | MEDIUM-HIGH | `IndependentSigningSession` accepted `options.verdictHash`, used it to compute the public `message` field, but then DROPPED it in `createMyReveal` and `aggregate` — both recomputed the signed message WITHOUT the verdict. A dispute (kind-39007) attestation produced through the independent-juror path therefore (a) signed the verdict-LESS message, (b) returned `verdictHash === undefined`, and (c) failed the round-4 validator's `verdict` binding. The round-4 fix had threaded the commitment through `crypto.ts`/`signing.ts`/`dispute.ts` but missed this wrapper | **FIXED** |

## Fixes

### 21. Thread `verdictHash` through `IndependentSigningSession`

`verdictHash` is now stored on the session and passed into both
`createRevealAndPartialSig` and `aggregateAttestation`, so every partial
signature and the aggregate commit to the same verdict-bound message that
`session.message` already advertised. Regression test runs a full 2-of-3
DKG + signing ceremony with a verdict commitment and asserts the aggregate
carries it and verifies against the verdict-bound message.

## Verified sound (no change)

- `dispute.ts::runDisputeOverrideSigning` threads `verdictHash` correctly
  (only `independentSigning.ts` had the drop).
- `courtSigningMachine.ts` deadline semantics are consistent: every action
  requires `now < deadline` and `tick` expires at `now >= deadline`, with
  no legal post-deadline transition to brick (unlike the round-2 vote
  machine case).
- `courtKeeper.ts` deterministic candidate stream, exclusion rules, and
  SHA-256 reveal verification are correct.
- `courtHostKey.ts` attestation/rotation/chain-resolution and the
  zeroizing `CourtHostKey` handle are sound (preimage excludes
  `hostSignature`; supersession is co-signed by the OLD key; strictly
  increasing timestamps rule out cycles).
